01 · Executive Summary

What this platform is — and why it matters

The Collections Orchestration Platform is a working, end-to-end system that takes inbound customer events across every channel (SMS, voice, email, dialer, payment processor), runs them through a real policy engine with compliance gating, dispatches the right action via a per-customer Temporal workflow, and invokes AI agents to handle complex cases — while landing every event in a real AWS S3 lakehouse for analytics and ML.

Every component inside the orchestration boundary is real. Compliance evaluations are real OPA policy calls citing §1006.6, §1006.14, and §1006.34. AI agent reasoning is real Anthropic Claude invocations with structured decision tools and persisted reasoning traces. The risk model is real sklearn.GradientBoostingClassifier trained on the actual customer event history. The lakehouse writes real Parquet to real S3 buckets that DuckDB queries in production-shaped patterns. The only thing that is simulated is the external channel traffic — which represents the world outside the system.

Three commitments the platform makes good on

1. Every decision is explainable and auditable.

Every OPA evaluation, every AI agent action, every compliance gate is persisted to a WORM (write-once-read-many) audit table with database-level triggers preventing UPDATE/DELETE. The full input, full output, and a correlation_id traceable end-to-end are captured.

2. AI is governed, not magical.

Every AI agent must close with a structured record_decision tool call — action, confidence (calibrated, not hardcoded), rationale, and parameters. No keyword matching on free text. The same agent feeds into the auditable agent_actions table the same way OPA does.

3. The orchestration boundary is real.

Channel simulation stops at the edge. Inside: real Temporal workflows, real OPA, real Postgres with WORM triggers, real Kafka with consumer groups, real S3 with Parquet, real DuckDB queries, real sklearn models trained on real history.

4. Compliance is a first-class concern, not a bolt-on.

Reg F §1006.6(b) quiet hours, §1006.14(b) multi-channel attempt caps, and §1006.34 validation notice tracking are wired into the workflow with auto-dispatch and immutable proof. Compliance events are emitted on PASS and FAIL, not fail-only.

03 · Platform Capabilities

Eight capability domains, each independently demonstrable

Real-time orchestration

Per-customer Temporal workflows over a Kafka event spine

Every customer has a long-running Temporal workflow that holds state (stage, active PTP, compliance flags, latest stats) and reacts to signals from a 3-partition Kafka topic keyed on customer_id. Independent consumer groups isolate the orchestrator path, the operational projector, and the lakehouse sink.

  • 3 Kafka consumer groups, 168h retention, partitioned by customer_id
  • Workflow auto-fires AI agents on actionable inbound intents; QC review on completed voice calls
  • Correlation IDs propagate channel → workflow → all downstream events
  • PTP lifecycle monitor + validation notice timer baked into the workflow loop
Proof: Open /platform → see service heartbeats with live throughput, per-partition Kafka offsets, consumer lag per group, end-to-end trace viewer keyed on event_id.
Policy engine

OPA-driven segmentation, treatment, routing & compliance

Six Rego policy modules express the entire decisioning surface as code. Every evaluation persists its input and output to strategy_audit_log — full lineage with strategy version, customer, and timestamp.

  • segmentation.rego — DPD bucket × risk tier × value segment
  • treatment.rego — action, message tone, AI-review-required flag
  • channel_routing.rego — recommended channels, fallbacks, contact window
  • compliance.rego — full suppression, written-only, frequency caps, quiet hours
  • transcript_audit.rego — FDCPA §807 prohibited language, Mini-Miranda, recording disclosure
  • ai_guardrails.rego — per-agent autonomy / escalation rules
Proof: /strategy → "Why did we do that?" runs one of four canonical cases through the live policy stack as a horizontal flow. Verbatim Rego output at every station.
AI agent platform

Five Claude-powered agents, governed and audited

Two agents are auto-invoked inside the workflow (Digital Channel on inbound HARDSHIP/DISPUTE/etc; Quality Compliance on completed voice calls). Three are on-demand (Case Reasoning, Portfolio Intelligence, Copilot for live human agents).

  • Every agent must close with a structured record_decision tool call
  • No keyword matching on free text · no hardcoded confidence
  • ~25 tools across DB reads, OPA calls, Kafka publishes, Postgres writes
  • Full reasoning trace + tokens + latency captured per invocation
  • claude-opus-4-7 with adaptive thinking for narrative + digest
Proof: /ai → live panel showing auto-fired counts per agent + recent actions with markdown rationale. The Activity Digest on a customer story is a real Claude call.
Compliance & audit

Reg F enforcement + WORM audit at the database layer

Compliance is wired through OPA at the action-dispatch gate and validated by a separate transcript-audit policy. Every audit row is immutable by Postgres triggers — UPDATE / DELETE raise.

  • §1006.6(b) quiet hours (8 am – 9 pm local) across voice, sms, dialer, digital
  • §1006.14(b) 7-in-7 voice cap + per-channel attempt caps + total-attempt cap
  • §1006.34 validation notice scheduled on first outbound + dispatched within 5-day window
  • Compliance events emitted on PASS and FAIL — full evaluation log, not fail-only
  • WORM triggers on strategy_audit_log, customer_events, ai_reasoning_traces, agent_actions, validation_notices
Proof: Try to DELETE FROM strategy_audit_log WHERE … at the SQL prompt — the trigger raises "Audit table is append-only; UPDATE/DELETE rejected".
Data lakehouse

Real AWS S3 medallion (Bronze → Silver → Gold)

Three real S3 buckets in us-east-1. A separate Kafka consumer group writes gzipped JSON Lines to Bronze every 30s. A scheduled compactor deduplicates by event_id and writes typed Parquet to Silver. A gold-builder runs DuckDB SQL across silver to produce four curated marts.

  • Bronze: topic= / date= / hour= Hive-partitioned ndjson.gz
  • Silver: snappy Parquet, explicit pyarrow schema, idempotent compaction via manifest
  • Gold marts: customer_360, portfolio_daily, strategy_performance, compliance_audit_daily
  • DuckDB+httpfs over S3 powers /api/lakehouse/query and the ad-hoc SQL UI
  • End-to-end data lineage: paste an event_id → see the same record materialized at Kafka, Postgres (WORM), Redis, Bronze (line N of file X), Silver (Parquet row), Gold (mart contributions)
Proof: /lakehouse → click a recent event chip. Six tier cards render with real S3 keys, raw JSON, Parquet rows, and mart contributions.
Risk & ML

Real model, real forecast, real significance testing

The lakehouse becomes a decision platform. A 25-feature feature store, a trained GradientBoostingClassifier, a Markov roll-rate forecaster, a two-proportion z-test for A/B significance, and a FinOps dashboard for AI spend.

  • Risk model AUC 0.669 on 1,500 real training rows (49% positive rate)
  • Local explanation: z-score × global importance, top-5 contributors per score
  • Roll-rate Markov from real stage_change events with 30/60/90-day projection
  • Champion vs challenger: lift, 95% CI on difference, p-value, required-n for 5% lift detection
  • AI cost: per-agent per-day token spend, $ from the published rate card
Proof: /risk-ml → score any customer; the top contributors trace back to specific behavioral features with z-scores. Retrain the model with one button.
Observability

Live tech-ops view across services, Kafka & OPA

Every long-running service emits a heartbeat with throughput, p99 latency, and error count. The API exposes Kafka topology (per-partition offsets, throughput, consumer lag) and a live feed of OPA decisions. Correlation IDs make every event traceable end-to-end.

  • Service heartbeat table with status, throughput/sec, p99, errors_5m
  • Kafka AdminClient queries for per-topic end offsets + consumer group lag
  • OPA decision feed surfaced live (input + output JSON per evaluation)
  • End-to-end trace: paste event_id, see every hop with timing
Proof: /platform → 3/3 services healthy with live throughput; Kafka topics with per-partition offsets; trace viewer.

07 · Roadmap

What we'd build next

The platform is feature-complete for a credible bank-grade demonstration. What follows is the sequenced path from POC to production, organized by horizon.

Now → 4 weeks

  • JWT auth + RBAC on the API and WebSocket layer
  • State-specific compliance overlays (NY DFS, CA Rosenthal, MA, TX)
  • Real STT pipeline (Whisper / Deepgram) feeding the transcript audit policy
  • OpenTelemetry tracing (Jaeger / Datadog APM integration)
  • Cost & rate-limit guardrails on Claude calls (circuit breaker)
  • Settlement & hardship structured workflows (real plan tables)

4 weeks → 3 months

  • Production deployment IaC (Terraform / CDK for AWS)
  • Migrate Kafka → Amazon MSK, Postgres → RDS
  • Multi-tenant + multi-portfolio architecture
  • Schema registry for Kafka events (AWS Glue / Confluent)
  • Customer self-service portal (the other side of the orchestration)
  • WhatsApp / Apple Messages for Business channels
  • Skip tracing / contact verification integration (LexisNexis stub)

3 → 9 months

  • Full MLOps platform: training pipeline, model registry, online serving
  • Champion / challenger with Bayesian uplift modeling
  • Customer-360 embeddings + similarity search
  • RAG over policy documents and resolved-case precedents
  • Regulatory reporting dashboards (CFPB exam-ready PDF/CSV exports)
  • Iceberg or Delta on the lakehouse (table format with time travel)
  • Cross-account orchestration (one customer · many products)

The roadmap is sequenced for compounding value: every item builds on the foundation already in place. Auth + IaC + OTel turn the demo into a deployable platform. State overlays + STT close the compliance gap. MLOps + RAG transform the AI agents from a feature into a flywheel.
